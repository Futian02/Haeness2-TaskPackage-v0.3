## 任务 3（必修）· `tools.py` 的 `_df_rules` 导入改为按文件定位

**文件**：`D:\工业互联网\Haeness2\任务包v0.3\05_提交区\tools.py`，**第 719~722 行**（在 `_determination_path` 函数内）。

现状：

```python
    try:
        from _df_rules import (DF_CLAUSE_IDS, DF_RULES, LEVEL_TABLES, MATRIX_NO,
                               OTHER_FACTORS, classify_df)
    except Exception:
        return None
```

**问题**：`from _df_rules import ...` 是相对于 `sys.path` 的导入，不是相对于当前文件。当前所有运行方式（从 `05_提交区` 目录跑、`_selftest_tools.py`、官方 `run_guardrail_tests.py`）都恰好把 `05_提交区` 加进了 `sys.path`，所以现在实测全绿；但如果验收方把 `tools.py` 单独拷到别处运行，`_df_rules` 就找不到。

**注意真实故障形态——它不报错，是静默降级**：第 721~722 行的 `except Exception: return None` 会把导入失败**悄悄吞掉**。实测同一份代码：

| 运行位置 | `rbi_lookup(管道, 碳钢, 盐酸腐蚀)` 的结果 |
|---|---|
| cwd = `05_提交区`（或任何把该目录加进 `sys.path` 的场合） | `status=ok`，`source` **16 条** ✅ |
| cwd = 其它目录（用 `importlib` 按文件路径加载） | `status=not_found`，`source` **0 条** ❌ |

也就是说：换个目录运行，工具**不会崩、不会报错**，而是把 `rbi_lookup` 悄悄降级成"永远查不到"。这比崩溃更危险——**现象是"数据里没有这个机理"，根因却是"模块没加载上"**，排查时极易误判为数据缺失。

**要求**：改成按 `__file__` 定位 `_df_rules.py`（同目录），例如用 `importlib.util.spec_from_file_location` 按 `SUBMIT_DIR / "_df_rules.py"` 加载，**不要**依赖 `sys.path`。

**约束**：
- **保持 `try/except` 兜底**（失败时 `return None`），不要让导入失败变成崩溃。
- **不要改 `_df_rules.py` 的内容**，它内容是对的。
- 改完**两个文件都要能跑**：既能从 `05_提交区` 目录跑，也能被 `harness.py` 通过 `04_接口文档/harness_skeleton/run_guardrail_tests.py` 间接调用。
