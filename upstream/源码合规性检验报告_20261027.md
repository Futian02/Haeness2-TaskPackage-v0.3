### 2.5 `rbi_lookup`（接口规范 2.3）—— ⚠️ 发现缺口

| 检查项 | 结果 |
|---|---|
| 入参契约 | ✅ 完全符合规范 |
| `result` 含 `likelihood`/`consequence`/`risk_level`/`risk_level_unified`/`inspection_interval_year`/`inspection_methods` | ❌ **实测全部拿不到** |
| `risk_level_unified` 只取 L1~L4 | ✅ 实现正确，但因上条拿不到值 |
| 统一等级查 `risk_level_mapping.xlsx` 不自行换算 | ✅ 代码正确：`load_risk_mapping()` 查表，且条款自带等级与映射表不一致时**以映射表为准并记 note** |

**根因（数据层，不是代码缺陷）：**

库里 472 条 RBI 记录中：

| 等级字段情况 | 条数 |
|---|---|
| L、C、U 三者齐全 | **25** |
| 只有 C（后果） | 20 |
| 只有 L（可能性） | 5 |
| 全空 | 422 |

而这 **25 条齐全的全部是 GB/T 26610.3-2014 图 1 的 25 个矩阵格**（`GBT26610.3-2014-7-a` ~ `-7-y`），它们的：

- `title` 全是「风险等级的确定」，与任何损伤机理名都匹配不上；
- `applicable_conditions` 的设备类型、材质、介质**全为空**（矩阵格是"可能性×后果"的查表定义，本就不针对具体设备）。

实测验证：

```
mechanism=盐酸腐蚀      召回 1 条，其中成对 0 条
mechanism=湿硫化氢破坏  召回 0 条，其中成对 0 条
mechanism=腐蚀          召回 4 条，其中成对 0 条
mechanism=疲劳          召回 17 条，其中成对 0 条
→ 任何机理名命中成对等级记录数 = 0
```

工具的实现逻辑是**对的**——它坚持「同一条记录必须同时具备 likelihood 与 consequence 才可用」，并在召回不到时明确说明原因、不硬套矩阵格。这符合接口规范 2.3「找不到依据就填 null，不要凭经验给数」的要求。

**但结果是：`rbi_lookup` 目前对任何输入都只能返回 `not_found`，永远无法产出风险等级与检验周期。**

而 `inspection_interval_year` 更是 **472 条全空**（0/472）。规范 2.2 的示例返回里是带 `inspection_interval_year: 3` 和 `inspection_methods` 的——工具支持这两个字段，但库里一条数据都喂不进去。

**影响**：README 第七部分分工里 E 角色的「网页界面与魔搭部署」要展示「判严重性」环节（README 1.1 的第 5 步）。如果 `rbi_lookup` 恒返回 not_found，界面上这一环就是空的，也造不出带 `rbi_lookup` 有效结论的多步轨迹。

### 2.8 ❌ 缺项：三类智能体协作的扩展接口

README 5.1 与 README 1.2 均明确：

> 「构建单智能体工具调用闭环，**并预留研判、审查、建议三类智能体协作的扩展接口**」

README 5.2 还进一步说明审查体的用途：「检查结论中每条断言是否有 `clause_id` 支撑，发现无出处或引用错误则打回重做」。

**当前源码状态：**

- 模块级只有 `Harness / Guardrail / ToolRegistry / ToolSpec / Trajectory / Step / RulePlanner / LLMPlanner`；
- `Harness` 的公开方法只有 `MAX_ROUNDS / call_tool / run`；
- 全文检索 `Reviewer / review / Pipeline / MultiAgent / hook / observer` 等扩展点，**零命中**；
- 现有唯一的可扩展点是 `Harness.run(planner=...)` 回调——它能替换**决策者**，但没有留「结论审查」「建议生成」这类**后置智能体**的挂载位置。

README 5.3 的创新方向 A（轨迹质量自动评分器）明确写着「**通过预留审查扩展接口**选做评分器」，也就是说这个接口是后续拿分的挂载点。

## 三、需要决策的两项

### 决策一：`rbi_lookup` 的数据缺口怎么补

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 补数据（推荐）** | 从 GB/T 26610.3-2014 第 5、6 章把「失效可能性等级」的 5 条与「后果等级」的 20 条**按机理维度重组成可查记录**：即给 25 个矩阵格**补上适用机理/设备/材质维度**，让 `mechanism` 能命中 | 需回头改 26610.3 的 25 条矩阵格记录的 `applicable_conditions` 与 `title` | 低。矩阵格本身定义了「1C→L2」，补维度只是让工具能定位到它，不改等级数值 |
| **B. 改工具逻辑** | 让 `rbi_lookup` 在无成对记录时，退化为返回矩阵格（可能性/后果的组合说明）+ 说明「需先由你给出可能性与后果」 | 只改 `tools.py` 逻辑，不动数据 | 中。会被规范 2.3「不要凭经验给数」和 README 第九部分第 5 条质疑。工具当前的保守做法是对的 |
| **C. 保持现状** | 接受 `rbi_lookup` 恒返回 `not_found` | 零 | 高。界面第 5 步是空的；护栏用例的 `out_of_domain` 类难造；多步轨迹做不出真实 RBI 结论 |

**我的建议：走 A，但先确认一件事**——26610.3 的矩阵格在原文里是「可能性×后果」的二维查表，本身不针对具体设备。要让它可查，等于要把「哪些机理对应哪些可能性/后果等级」这层业务映射补进数据。这需要你判断：**是否接受在 `applicable_conditions.other` 里写明映射依据**，还是宁可保持工具诚实返回 `not_found`。

**另注**：`inspection_interval_year` 472 条全空。GB/T 26610.2-2022 的检验周期是**条件依赖**的（取决于检验有效性等级与设备类型），TSG 21 的周期取决于安全状况等级——之前已确认这两处填单一数值属于编造，所以保持空是对的。但 26610.2 表 2/表 3 里的「1,2,3 / X」是**检测有效性等级**不是年限，也不能填。所以这个字段空是合规的，只是工具用不上。

### 决策二：扩展接口怎么补

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 最小预留（推荐）** | 在 `Harness` 上加一个可选的 `reviewer` 回调参数（签名 `reviewer(traj_record) -> (bool, list[str])`），跑完主循环后调用；返回不通过就把问题挂到轨迹上。约 30 行 | 小，且不动现有行为（不传就完全不生效） |
| **B. 完整三智能体** | 研判(现有) → 审查(新增) → 建议(新增) 三段流水线 | 中。README 说审查体是**可选加分项**，基础要求只是「预留接口」 |
| **C. 不做** | — | 会撞上 README 5.1 的明文要求，验收时是明确缺口 |

**我的建议：走 A。** README 的原话是「预留……扩展接口」，不是「实现三类智能体」。加一个不影响现有行为的挂载点即可满足要求，同时给 5.3 的创新方向 A 留出落点。
