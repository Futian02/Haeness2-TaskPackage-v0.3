### 🟡 问题 3（功能·轻微）：`tools.py` 依赖 `from _df_rules import ...` 的相对导入

`tools.py:719` 在函数内做 `from _df_rules import (...)`，这是**相对于 `sys.path` 的导入**，不是相对当前文件的导入。当前所有运行方式（从 `05_提交区` 目录、`_selftest_tools.py`、官方护栏脚本）都恰好把 `05_提交区` 加进了 `sys.path`，所以实测全绿。

**风险（实测确认为静默降级，不是崩溃）**：官方 `run_guardrail_tests.py` 从 `04_接口文档/harness_skeleton/` 导入 harness，靠 `harness.py` 内部的 `_find_submit_dir()` 才走到 `05_提交区`。实测同一份 `tools.py`：

| 运行位置 | `rbi_lookup(管道, 碳钢, 盐酸腐蚀)` |
|---|---|
| cwd = `05_提交区` | `status=ok`，source **16 条** ✅ |
| cwd = 其它目录（`importlib` 按路径加载） | `status=not_found`，source **0 条** ❌ |

因为第 721~722 行的 `except Exception: return None` 把导入失败**吞掉了**，所以换个目录运行**不报错、不崩溃**，而是把 `rbi_lookup` 悄悄降级成"永远查不到"。**现象像"数据里没这个机理"，根因却是"模块没加载上"**，排查时极易误判为数据缺失——比直接抛异常更危险。

**建议**：改成 `importlib.util.spec_from_file_location` 按 `__file__` 定位 `_df_rules.py`，或把规则内联进 `tools.py`。**属稳健性改进，不影响当前验收。**

**根因是标准性质决定的，不是漏填**：26610.2/3/4/5 的条款主体是**因子赋值表**（"1 级、2 级、3 级"）与**矩阵格**，原文本就不针对具体设备/材质/介质。这 472 条是"表格行级条款"，不是"设备级条款"。

**实际影响（已实测确认边界）**：
- `rbi_lookup` 不给 mechanism → `not_found`，message 明确说"applicable_conditions 为空，无法按 equipment_type/material 检索" ✅ 行为诚实；
- 给 mechanism → 走**判定路径**（DF=2 依据 + 五因子需补充什么 + 六项相加查表1/表2/表9/图1），`source` 16~17 条**全部真实存在** ✅；
- 25 个有完整等级的矩阵格**可被取到**（`mechanism='风险等级的确定'` → 返回 L1 + 低风险）✅，只是走不了机理名路径。

**结论：这不是缺陷，是标准结构的如实反映，且工具行为诚实。但做 B 阶段轨迹时必须知道——`rbi_lookup` 步骤的 `observation` 只能是"判定路径"，不能写成"得出 L3 风险等级"**，否则就是编造，会撞 README 第九部分第 5 条。

### 🟢 问题 6（提示性）：`damage_mechanism_query` 对极端温度不报超范围

实测 `temperature_c=2000`（碳钢+氯化氢）返回 `status=ok, in_domain=True` 且 `message` 为空。

**根因**：库中 DM 条款温度区间共 82 条——完全开区间 `[null,null]` **59 条**（原文未给温度界限）、单侧开区间 13 条、双侧闭区间 10 条；**有上限的仅 13 条，最大 925℃**。工具按"该条款自身的上下限"判定，2000℃ 不违反任何一条的开区间。

**是否算错**：不算——README 2.5 要求"查询条件超出**条款覆盖范围**时"才 in_domain=false，而条款本身未设上限。但 **message 为空**会让界面上这一环无解释。建议在温度超出全库最高上限时补一句提示。
