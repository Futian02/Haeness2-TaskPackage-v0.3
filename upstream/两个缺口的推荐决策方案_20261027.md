# 两个缺口的推荐决策方案

> 时间：2026-10-27 17:50
> 依据：本轮实测 + `03_案例样例/标注示范.md`（官方示范）+ README / 工具接口规范

---

## 一、决策一：`rbi_lookup` 数据缺口

### 推荐：**C —— 保持现状，不补数据、不改工具逻辑**

（我上一轮建议的 A「给 25 个矩阵格补适用维度」，经过本轮深查**已自行推翻**，理由见下。）

### 为什么推翻 A

A 方案的前提是「矩阵格可以补上适用机理/设备/材质维度」，让 `mechanism` 能命中它。我实测验证了这个前提，**它不成立**：

**验证 1：DF 表按机理分类，但只有 16/82 个机理能对上**

GB/T 26610.3-2014 的 5.2.2「损伤因子(DF)」确实是按机理分类的（DF1=腐蚀开裂、DF3=热疲劳或机械疲劳、DF4=高温氢腐蚀…）。但拿库里 30579 的 82 个机理名去对：

```
DF1 腐蚀开裂              → 11 个机理
DF3 热疲劳或机械疲劳      →  2 个
DF4 高温氢腐蚀            →  1 个
DF8 蠕变                 →  1 个
DF9 材料退化             →  1 个
DF2 脆性断裂             →  0 个
DF5 奥氏体不锈钢应力腐蚀开裂 →  0 个
DF6 局部腐蚀             →  0 个
DF7 全面腐蚀             →  0 个
DF10 其他损伤机理          →  兜底，82 个全落此项
```

**82 个机理里 66 个会落到兜底类**。补维度就意味着给 66 个机理编一个「它属于哪一类」的映射——那是**标准里没有的业务判断**，不是摘录。

**验证 2：可能性等级本来就不是单条机理能定的**

5.1.2 原文写得很清楚：

> 「将上述 **6 个因子**的值相加，计算失效可能性因子，按表 1 确定失效可能性等级」

六个因子分别是：

| 因子 | 赋值依据 | 依赖什么 |
|---|---|---|
| EF 设备因子 | 评估范围内可能失效的设备总数 | 装置规模 |
| DF 损伤因子 | 是否存在发生某损伤机理的可能性 | 机理识别 |
| IF 检验因子 | 检验历史与检验方案 | 检验记录 |
| MCF 维护状态因子 | 管理水平、设计制造水平、维修方案有效性 | 企业管理 |
| PF 工艺因子 | 年停工次数、工艺稳定性、保护装置可靠性 | 运行数据 |
| MDF 机械设计因子 | 设备设计与现行标准的符合性、工艺特殊性 | 设计文件 |

**六个里有五个依赖装置级现场信息**，与「某机理」无关。后果侧同理：6.3.1.2 是「6 个因子相加查表 2」，6.4.2.2 是「4 个因子相加查表 9」。

**验证 3：GB/T 26610.4 给的也是因子，不是机理级等级**

26610.4 共 139 条，逐一查看全部是「次因子赋值表」（工厂条件次因子、寒冷气候运行次因子、设备复杂性子因子、建造规范次因子、寿命周期次因子、操作压力子因子…），**没有一条给出「某机理在某设备上的等级」**。

### 为什么 C 才是对的

**决定性证据在官方样例里。** `03_案例样例/标注示范.md` 第 397 行，官方把「工具查不到就不写」列为**模板的四个优点之一**：

> 「**工具查不到就不写**。第 3 步 `rbi_lookup` 返回 `not_found`，结论里就不出现风险等级和检验周期，也不引用任何 RBI 条款号。」

官方示范 UG-DEMO-0002 的 `rbi_lookup` **本身就返回 `not_found`**，示范的结论明确写：

> 「风险等级与检验周期当前条款库无法给出，待 RBI 条款入库后用 `rbi_lookup` 重新查询。」

第 15 行的说明更直接：

> 「最小库不含 RBI 条款，因此 UG-DEMO-0002 的 `rbi_lookup` 返回 `not_found`，**不编造风险等级或检验周期**」

也就是说：

- **`not_found` 是被官方示范认可的正确行为，不是缺陷**；
- 工具当前的实现严格符合这个要求——坚持「同一条记录必须同时具备 likelihood 与 consequence」，召回不到就明说原因，**不硬套矩阵格**；
- 接口规范 2.3 也明写：「找不到依据就填 `null`，**不要凭经验给数**」。

**A 方案的风险是实质性的**：给 25 个矩阵格编造适用机理维度，等于让工具**看起来能判级、实际是套用未经标准授权的映射**。这直接撞上 README 第九部分不合格情形第 5 条「超出适用范围仍返回 `in_domain: true` 并给结论」，以及规范 2.3 的「不要凭经验给数」。

### 那 rbi_lookup 是不是就没用了？不是

它的真实价值在**多步轨迹的第 3 步**：模型查完机理后调用 `rbi_lookup`，得到 `not_found` + 明确说明「哪些因子还没定」，于是**下一轮去查因子表**（`standard_clause_search`），或者在结论里诚实写「风险等级需待六因子齐备后判定」。这正是官方示范展示的推理链形态。

**这恰恰是护栏与轨迹最需要的素材**，而不是一个硬造出来的等级。

### C 方案的代价与应对

| 代价 | 应对 |
|---|---|
| 界面第 5 步「判严重性」展示的是 `not_found` | 界面如实展示「RBI 等级需六因子齐备后判定，本条款库未提供装置级因子数据」——这本身就是过程可视（README 指标(1) 要的就是让评审看到模型怎么走的） |
| 多步轨迹第 3 步的 `result` 是空的 | 合法。`status=not_found` 时 `source` 本就该为空（只有 `status=ok` 才强制非空）。轨迹的价值在 `thought`/`observation` 的推理链 |
| 护栏 `out_of_domain` 类用例难造 | **不难造**。用超出库覆盖范围的输入（如材质 S22053 + 介质组合）即可触发，官方示范 UG-DEMO-0003/0005 就是这么做的 |

### 唯一需要动的地方（一处小改）

当前 `rbi_lookup` 的 `message` 里有一句是**技术自述**，不适合给评审看：

> 「（另需说明：库中 RBI 记录未登记适用设备与材质，本次仅按机理名检索，equipment_type / material 未参与筛选。）」

这句应该删掉或改写成面向使用者的说明。**其余全部不动。**

## 二、决策二：三类智能体协作的扩展接口

### 推荐：**A —— 最小预留（加一个可选 `reviewer` 回调）**

### 理由

**1. README 的原话是「预留接口」，不是「实现三类智能体」**

README 5.1：

> 「本科生基础要求是完成**单智能体 + 工具调用 + Harness**闭环……**并预留**研判、审查、建议三类智能体协作的扩展接口。**三类智能体协作的实现属于后续扩展**，审查体仅为可选加分项。」

区分得很清楚：基础要求 = 预留；实现 = 后续扩展 + 可选加分。

**2. 它是创新方向 A 的落点，值得留**

README 5.3：

> 「**A. 轨迹质量自动评分器** —— 通过预留审查扩展接口选做评分器……**中，最推荐**」

「最推荐」四个字说明这个挂载点有实际价值，而且评审会看。

**3. A 的实现成本和风险都最低**

- 约 30 行，不传就完全不生效 → **现有行为零变化**，不会动到已通过的 17 项自测和 5 条 demo 轨迹；
- 相比 B（完整三智能体流水线）要少写两个智能体的调度逻辑，而基础要求根本不需要；
- 相比 C（不做）能直接消掉一个 README 明文缺口。

**4. 具体接口设计**

```python
# Harness.run 增加可选参数
def run(self, traj_id, task_input, planner,
        special_type=None, annotator="", checked=False,
        reviewer=None):          # 新增：可选审查回调
    ...
    # 主循环结束后，若提供了 reviewer，则调用一次
    if reviewer is not None and traj.final_answer:
        verdict = reviewer(traj.to_record())
        # verdict 形如 {"passed": bool, "issues": [str, ...]}
        traj.review = verdict        # 记入运行日志，不进数据集
        if not verdict.get("passed", True):
            # 打回重做：把问题写进 observation，留痕但不导出
            ...
```

约束：
- `reviewer` **不传则完全不生效**，现有行为一字不变；
- 审查结果只进 `to_dict()`（运行日志），**不进 `trajectories.jsonl`** —— 因为 `trajectory.schema.json` 的 `additionalProperties: false` 不允许加新字段，且数据集格式是硬约束；
- 这正好对应 README 5.2 描述的审查体职责：「检查结论中每条断言是否有 `clause_id` 支撑，发现无出处或引用错误则打回重做」。

**5. 顺带的好处**

审查回调能立刻拿来当**轨迹质检器**——README 第九部分第 6 条「200 条里 190 条是同一模板换参数」和第 2 条「`basis` 里的 clause_id 查不到」正是脚本查不出来的两类问题，一个 reviewer 回调就能覆盖。等于给 E3「人工抽查」省下大量时间。

## 三、两个决策的汇总

| 决策 | 推荐 | 动作量 | 是否动数据 |
|---|---|---|---|
| `rbi_lookup` 缺口 | **C 保持现状** | 改 1 句 `message` 文案 | **不动** |
| 扩展接口 | **A 最小预留** | 约 30 行，加可选 `reviewer` 回调 | 不动 |

**合起来：只动 `tools.py` 的一句文案 + `harness.py` 约 30 行。不改任何数据，不影响已通过的测试。**

## 四、如果仍想做点别的，还有第三种可能

若你希望 `rbi_lookup` 在界面/轨迹里「看起来有等级」，还有一个**不违反规范**的做法：

**把因子表补成可查记录**——即让 `rbi_lookup` 在 `not_found` 之外，额外返回「判定该机理等级需要哪几个因子、每个因子的赋值依据在哪条」。这不需要编造任何等级，只是把库里已有的 DF/EF/IF/MCF/PF/MDF 因子条款按机理线索组织起来返回。

但这属于**扩展工具功能**，而接口规范 2.3 明确定义了 `rbi_lookup` 的返回结构是 `likelihood/consequence/risk_level/...`，加新字段可能撞上「不得自行增减」的约束。所以这条路要等你确认规范口径，我不擅自做。
